# GraphRAG 隔离实验：它对"全局聚合型问题"到底有没有用？

**结论先说：在这个语料上，实体图的增益是负的；真正起作用的是"按文档去重"，而它几乎零成本。**

| 方法（最终都只取 4 份文档） | 平均文档覆盖率 |
| --- | --- |
| 生产同款：向量 top-8 → 精排 → 取 top-4 **chunk** | **23.3%** |
| 向量 top-8 → 精排 → **每份文档只留最好的 chunk** → 取 top-4 文档 | **73.3%** |
| 实体图（8 候选）→ 精排 → 按文档去重 | **13.3%** |
| 向量 top-40 → 精排 → 按文档去重 | 80.0% |

---

## 为什么做这个实验

GraphRAG 的价值主张是回答"全局聚合型问题"——答案不在任何单个 chunk 里，而散落在多份文档，
必须汇总才能答全。例如"「工作日」这个时限在哪些制度里出现？分别要求几个工作日？"

主评测集（`evals/`）里的 54 条用例全是单跳/双跳的单点问题，一条这样的题都没有，
所以**主评测根本测不出 GraphRAG 的价值**。要做这个判断，必须先造靶子。

## 方法

**靶子**：`questions.json` 里 5 条全局聚合题，每条要求覆盖 2–3 份文档。

**四条对照臂**，全部使用同一个精排模型（cross-encoder），最终都只保留 4 份文档：

| 臂 | 候选来源 | 收敛方式 |
| --- | --- | --- |
| `baseline` | 向量 top-8 | 直接取精排前 4 个 **chunk**（生产行为） |
| `dense8` | 向量 top-8 | 精排后**每份文档只留最好的 chunk**，再取前 4 份文档 |
| `graph8` | 实体图命中（截断到 8 个） | 同上 |
| `wide40` | 向量 top-40 | 同上 |

`dense8` 是关键的**对照臂**：它和 `graph8` 候选预算完全一样，唯一差别是候选来自向量而不是图。
没有这一臂，就无法区分"图有用"和"候选变多有用"——第一版实验只有 `baseline` 和 `graph`，
看到 23.3% → 76.7% 就以为图有效，其实是候选数（17~35 个）在起作用。

**图的构建**：`build.py` 用 LLM 对每个 chunk 抽 2–8 个实体（只保留能在原文找到字面的，
防止造词），建 `实体 → chunk` 与 `chunk → 实体` 双向索引；查询时用**二元组重叠**匹配问题与实体，
再做 1 跳扩散。产物 `entities.json` 已入库，复现实验不需要密钥。

## 三个结论

1. **真正的瓶颈是"top-4 都落在同一两份文档上"，不是"缺少图"。**
   聚合型问题要求覆盖多份文档，而纯 top-k chunk 天然会给出同一文档的多个相邻段。
   一个"每份文档只留一条"的收敛步骤，在**候选预算不变**的前提下把覆盖率从 23.3% 提到 73.3%。

2. **实体图在等预算下更差（13.3% vs 73.3%）。**
   原因是实体匹配噪声大：二元组匹配会把「工作分析」「安然公司」「奖惩制度」这类
   只有部分字面重合的实体也拉进来，候选质量反而不如向量 top-8。
   而这套图的构建成本是 **126 次 LLM 调用 / 129 秒 / 约 ¥4**，并且**文档一改就要重抽**。

3. **放宽候选仍有边际收益（73.3% → 80%），但代价很大。**
   精排 40 个候选在本机约 25–40 秒，而生产链路整体才 3~5 秒。
   所以"全量放宽候选"不可行，正确做法是**先判断问题类型再决定要不要放宽**。

## 对主项目的影响：没有合入

三条理由，都写在这里，将来有人问"你为什么不用 GraphRAG"可以直接看：

1. **权限模型冲突。** 主项目的权限是每次请求在 chunk 层预过滤（`principal.allowed_groups`）。
   GraphRAG 预生成的社区摘要是**一段混合了多份文档内容的自然语言文本**，无法做行级过滤，
   等于把"权限靠结构不靠提示词"这条打穿。
2. **证据链退化。** 主项目的答案门槛要求 citation 指向具体文档与段落；
   摘要只能给出"社区 N"，刚做的答案层评测（`citation_precision` 100%）会失去意义。
3. **测不出正收益。** 等预算下图的覆盖率低于向量检索（13.3% vs 73.3%），
   而它带来构建成本、增量更新成本、以及 CI 需要密钥。

## 边界（这个实验不能证明什么）

- **只有 5 条题、126 个 chunk**，样本很小；结论适用于"制度类小语料"，不能外推到大规模知识库。
- 图的实现是**轻量版**（实体共现 + 1 跳扩散），没有做社区检测与社区摘要。
  微软那套 GraphRAG 的核心是"社区摘要"，本实验**没有**覆盖它——那部分要另做实验。
- `dense8` 的提升也可能部分来自"精排分数阈值被我放宽了"（实验里用 `threshold=-999`
  保留全部候选再收敛），与生产的阈值策略不同，需要单独验证。

## 一句话

> 我原本以为聚合型问题需要图。实验显示它需要的是**多样性**——
> 而多样性用一个 20 行的"按文档去重"就能拿到，不需要 126 次 LLM 调用。
